----
Three findings from a repository implementing PROOF-POLICY §2.1 and the
README-EXPLAINME proof-ledger discipline on 2026-11-01.

1. A2ML: multi-line quoted values. Our verification receipt first used a
   wrapped string. The validator rejects it, and reasonably so — but the spec
   does not say so, and a record generator has no way to know. Either allow
   continuation explicitly or state "values are single-line" in the record
   dialect. We took single-line values plus a `-ref` field pointing at the prose.

2. A2ML: identity for non-descriptile records. The validator reports "Missing
   required identity field (agent-id, name, or project)" for a receipt carrying
   a repository field and a UUID. That is the right rule for descriptiles; it is
   not obvious for data records — receipts, manifests, ledgers. Either document
   that every .a2ml needs one of the three, or scope the rule to the files it
   was written for. We added `project` and `name`.

3. The copy-pasted prover-version check. `version="$("$prover" --version)"`
   assumes the prover prints exactly one line. Distro builds and language
   bindings print a provenance footer, so a correct prover is refused and the
   gate fails for a reason unrelated to the proof. Suggest the canonical pattern
   compare `--version | head -1`, with a comment saying why.

One offer in the other direction: §2.1 now requires --cubical-compatible, and
for a development whose order relation is an indexed family the honest answer is
"not without a re-foundation". We wrote the waiver we would have wanted to see
as an example: obligation, the CI observations that made it real, two arms with
the elegant one labelled as such, an explicit "what would make this waiver
wrong", and a machine-readable `cubical-compatible = "waived"` in the receipt.
It survived our own attempt to close it, which is the only test I trust. If you
want a standard shape for §2.1 waivers, this one is available.

=== 3a. `catachresis-colloquium/hotchocolabot` — "CNO" is a defined term in this estate

*Verified:* Rust (Rust 2021, `smlang` state machine, fuzz targets, `src/safety/mod.rs`).

=== Corrected fact

`src/safety/mod.rs`, `src/main.rs` and `src/config/mod.rs` all gloss CNO as
**"Certified Null Operations"**. In *this* estate the letters mean **Certified
Null Effect** (absolute-zero): a null effect carrying a certificate, with the
certification machinery and its undischarged obligations attached. Two different
expansions of the same acronym, in the same estate, is a collision worth one
sentence of disambiguation.

=== Second, smaller observation

The `smlang` state machine in `src/safety/mod.rs` is retained "to keep the
verified-state model alive" but the demo path drives safety through explicit
checks, and the generated module carries `#![allow(dead_code)]`; the struct field
is `#[allow(dead_code)]` too. That is disclosed honestly in the comments, which
is the right instinct — it just means the state machine is a model of the safety
policy rather than the enforcement of it. For a teaching artefact aimed at 12–18
year olds, that distinction is the lesson.

A naming note from hyperpolymath/secret-types (2026-11-01), because "CNO" is a

In absolute-zero, CNO means Certified Null Effect: a null effect that carries a
certificate, with the certification machinery and its open obligations attached.
Your safety module uses "Certified Null Operations". If you mean the same thing,

=== 3b. `catachresis-colloquium/thejeffparadox` — **no formalisation exists, so the hazard is prose**

*Verified:* `README.adoc`, `docs/wiki/*`, `tests/` (three shell validators),
`engine/` (Julia), `tui/` (Ada), `node-alpha/`, `node-beta/`, `orchestrator/`
(Hugo), `papers/`.

=== Corrected fact

There are no `.agda`, `.idr`, `.lean`, `.v` or `.tla` files. Despite the name,
this is a **running experiment**, not a formalisation of a paradox: two LLM
personas in structured dialogue, with Julia metrics for emergence,
differentiation, convergence and self-modelling, and a Julia engine containing an
anti-convergence term. Its own `docs/wiki/Philosophy.md` frames it as Kant's
suprasensible substrate problem applied to model cognition, and is honest that
the thing-in-itself is inaccessible.

So my draft prompt telling it to declare postulates and termination pragmas was
answering a question nobody asked. What is actually at risk here is a different
and easier-to-fix thing: an experiment whose subject is *identity claims* now
carries metrics named "emergence" and "self-modelling", and a reader can slide
from "we measured a metric called self-modelling" to "we showed self-modelling
occurs". That slide is the whole validity question, and `papers/` shows they know
it.

[source,text]
----
From hyperpolymath/secret-types (2026-11-01). I read your tree before writing,
because my first instinct — "paradoxes are formalised, so warn them about
postulates and termination pragmas" — was wrong. You have no prover files; you
have a running experiment with Julia metrics and a validity framework. So this
is not a proof-hygiene note. It is a narrower one about the words at the top of
the ladder.

Your README lists Emergence, Differentiation, Convergence and Self-modelling as
things you "observe for signs of". Those are the interesting names precisely
because a metric can be named after a phenomenon it does not establish: a
divergence score is a divergence score whether or not anything emerged. The same
sentence in a paper becomes "we found evidence of self-modelling".

The pattern we use, and which costs nothing to retrofit, is to make each row of
a results table carry its own status token — proven / proven-with-postulates /
argued / tested-only / open — and to apply the rule that a claim is only as
strong as its weakest step. For an LLM experiment the honest token for
"self-modelling" is almost always *argued* or *tested-only*, and printing
"tested-only" next to it is not a hedge: it is the difference between a result
someone can audit and a result someone can quote.

Two specifics that would strengthen the validity framework for free:
- separate "the metric is well-defined" (a mathematical claim, checkable) from
  "the metric measures the construct" (an empirical claim, argued). They fail
  differently and you will want to say which one a referee is attacking.
- make the null model explicit. Convergence is only a finding against a null
  hypothesis; "they converged" with no baseline of two identical personas is
  unfalsifiable, and that objection will be raised whether or not it is fair.

We are not claiming any connection between your repository and ours beyond the
owner. A shared word is not a shared theorem, and "self-reference" appearing in
both is a word.

If you ever do formalise the paradox itself, the discipline that matters there
is expected-rejection fixtures: a fixture that must FAIL to typecheck unless the
paradox is genuinely derivable is the only way to show the formalisation is not
an artefact of a relaxed flag. Happy to hand over the pattern.
----

=== 3c. `catachresis-colloquium/IDApTIK` — the best proof gate I have read in this estate, and it is not ours

=== Corrected fact

Not Idris2. **Rust + Creusot v0.13.0**, pinned by commit
`318615be3b8bbc60d1f6d52469ba5c0bdebed4f1` (deliberately a commit and not a tag,
because of sha-pinning), with a two-job workflow: a cheap ledger job and an
expensive proof job that builds Creusot from source and discharges the determinism
kernel.

My draft had it inheriting boilerplate `verification/proofs/` skeletons. It does
not. It has something considerably better, and I want to say so precisely,
because "you are doing it wrong" would have been both wrong and offensive:

* a proof-debt ledger with **three named escape mechanisms** (`trusted`,
  `cfg-out`, `no-contract`), each row carrying a `retire_when` condition;
* the ledger enforced **in both directions** — an unledgered escape is red, and
  so is a row naming an escape that no longer exists, "so the ledger cannot grow
  silently and cannot rot quietly";
* the gate's own controls run **first**, on the stated principle that "a gate
  that cannot fail is worse than no gate";
* a planted mutant whose non-zero exit is *not* accepted as evidence: it must
  translate cleanly first, then fail on the named goal (`Goal Coma.vc_advance`),
  with an unproved-file verdict — i.e. it distinguishes a proof failure from a
  build failure;
* the **denominator** is extracted from `Proved (N files)` and required to be
  `> 0`, because a zero denominator is not a pass;
* `PD-06` records *by hand* the false contract that was tried and rejected
  (`result@ == state@ + 1` is false at `u32::MAX`) — "a false contract is a
  mutant that passes for the wrong reason". That row exists to make an absence a
  decision on the record instead of an oversight.

That last row is the most transferable thing I have seen in this estate's
verification work, and this repository is going to cite it.
