| `npm install @asciidoctor/core@2.2.9 @asciidoctor/cli@3.5.0`
| `scripts/check-adoc-renders.sh` green over all 168 tracked `.adoc`

The third row is the one that earned its place by failing first, and it is worth
the paragraph. CI installs the Ruby gem `asciidoctor` 2.0.26; this sandbox
cannot reach `rubygems.org`, so the first attempt used `@asciidoctor/core@4.1.1`,
the newest available. That build rendered **all 168 files clean** — and CI then
failed the very same gate on
`dropping cells from incomplete row detected end of table` in
`docs/reports/status/toolchain-and-version-pins-2026-11-01.adoc`: a table where
one row carried three cells into a four-column layout. Asciidoctor 2.0.x calls
that an error; 3.x core silently pads the row.

So the rule this repository now applies to its own instruments: **a render check
is only a check if its parser is the parser the gate uses.** The fix was to pin
the sandbox parser to the core version the CI parser tracks (2.2.9 is Asciidoctor
2.0.23, one patch line from 2.0.26), after which the local run reproduces CI
exactly. `scripts/dev-toolchain.sh docs` installs that one, and says why.

The Agda arrangement is ugly and worth stating plainly: the binding is not
usable without the data directory, and the wheel does not ship it, while the
npm package ships the data directory for both 2.6.4.3 and 2.7.0.1. "Agda
installed" and "Agda usable" are different claims; only the second is recorded
here.

moving one changes every receipt below it.

never produces a receipt (CI does). If the sandbox is ever allowed to produce a
receipt, the two pins must be reconciled first.

== The canon pin: the gate that cannot check it, and the check done by hand

`Canon lockstep` fails on this branch, and it fails on `main` at `f581f82` for
the same reason. The failure is not drift in this repository; it is the job.

The job fetches the profile it intends to compare:

[source,sh]
----
URL="https://raw.githubusercontent.com/hyperpolymath/rsr-template-repo/${HEAD_SHA}/${p}"
----

`HEAD_SHA` is *this* repository's commit, and the URL names the **template**
repository. A commit that exists here does not exist there, so the fetch 404s on
every repository except a template running on its own commit. The error it then
prints — "no rsr-profile.a2ml at `93a22e3` — this repo cannot declare a canon
pin" — is therefore false of this repository in two ways: we do have
`.machine_readable/rsr-profile.a2ml`, and the job never looked at it. The
intended URL would 404 as well: `hyperpolymath/rsr-template-repo`'s
`.machine_readable/` carries no `rsr-profile.a2ml` at `main` either.

So the pin was checked by hand on 2026-11-01, against `canon.lock` fetched from
`hyperpolymath/standards` (which redirects to `metadatastician/standards`):

[cols="1,3,1",options="header"]
|===
| Pin | Value | Verdict

| `[canon].version`
| `2.1.1` declared; `2.1.3` in `canon.lock`
| **was drifted, corrected**

| `criteria_sha256`
| `6a5aa8857bd0d0d58ef48827938ca17c251b6b854dacf59d306388d61694d82a` on both sides
| **matched**

| `gates_sha256`
| `e70efd2f…` declared, `2f31f46d…` in `canon.lock`; the hash of
  `.machine_readable/template-capability-gates.toml` at `main` today is
  `2f31f46d…`
| **was drifted, corrected**
|===

The criteria hash being identical is the load-bearing part: the criteria set did
not move, so this repository is scored against exactly what it was scored
against before. What moved is the gate table, and `canon.lock`'s own 2.1.3 entry
says why — "the gate table can see nested layouts", detection-rule corrections,
with no criterion added, removed, re-tiered or re-gated. Adopting it is
therefore a correction of a false statement, not a policy change, which is the
only kind of pin move this repository makes without an owner ruling.

Two things found while doing it, neither fixed here because both are decisions
larger than the pin:

* This profile is **the template's file, verbatim**. It declares
  `role = "spine"`, which this repository is not, and it declares the maximal
  capability set including `cli`, `container`, `benchmarks` and `docs-site` on
  the strength of scaffolding rather than of code. The oracle scores a
  capability-gated criterion only when the capability is declared, so a
  template-maximal declaration here asks to be scored against modules this
  repository does not carry — the over-scaffolding failure the profile's own
  comment warns against. Writing a repo-specific profile is the right fix and it
  changes the scored criteria set, so it needs a decision rather than a patch.
* `canon.lock` puts `version = "2.1.3"` beside `released = "2026-09-30"` and
  `tag = "canon-v2.1.2"`. The release point's tag lags its version line; a
  consumer resolving the tag to audit 2.1.3 would get 2.1.2's tree. Worth one
  line in the standards prompt in
  `docs/reports/handoff/out-of-scope-prompts-2026-11-01.adoc`.
