[abstract]
This is the canonical scope statement for the standalone `secret-types`
repository: a confidentiality-label / information-flow research project. It
records the owner's decision of 2026-10-04 to keep this as its own repository
(which supersedes the earlier "mint it or fold it into `epistemic-types`#32"
alternative), the ruling of 2026-09-30 on the model direction, and a first
specification proposal for a two-level, confidentiality-oriented
information-flow discipline over pure, deterministic, total programs.

*This document is the scope statement; since 2026-10-19 its model is also
implemented and partly proved in this repository* (<<status_of_the_model>>). The
two are kept side by side and neither may outrun the other: the prose states what
the fragment is, and `PROOF-STATUS.adoc` names a module for every claim graded
PROVEN. Still absent, and deliberately so: a `Secret ℓ A` value type in a
programming interface, a declassification rule, runtime enforcement, any
cryptographic or side-channel guarantee, and any statement about terminating
runs. No other repository imports any artefact from this project, and no
consumer or frontier item has been selected for it.

== Scope statement

*Question.* Which value flows does a confidentiality label permit, and what may
a lower (less cleared) observer learn from an output? A value type `Secret ℓ A`
classifies a value at a label `ℓ`; the first model uses a two-level
`Public ⊑ Secret` label order over a pure, total calculus, and the target
property is termination-insensitive noninterference between secret inputs and
public observations.

*Boundary.* A label is not cryptography and not an epistemic standpoint. A
`Secret ℓ A` does not make a value unreadable, does not authenticate a
principal, does not enforce runtime access control, and does not hide timing,
storage, network or other side channels. The baseline below declassifies
nothing: an ordinary `Secret`-to-`Public` flow is outside the discipline, and
any release needs a separate policy and theorem. A security label is also not
an epistemic availability index (`κ`); the two share the shape of an order and
nothing else. *No consumer and no frontier item is selected* (confirmed
2026-10-04, unchanged on 2026-11-01): the possible RMO key-provisioning /
disclosure use is an inference recorded in valence-shell's direction doc, not a
claim made here (see <<consumers_and_provenance>>).

So the honest status sentence is: *the fragment is implemented and its theorem is
proved; the specification's non-claims still hold in full.* What that buys and
what it does not:

* **Buys.** A machine-checked two-run property for a `while` language with fuel
  semantics, at any `Lattice` and any down-closed observer; explicit and implicit
  flows refused by the typing rules and shown to leak when the rules are removed;
  a certificate of which lattice laws the proof consumes and a countermodel for
  each when dropped. Every module is `--safe --without-K --no-libraries`,
  double-checked, with no postulates.
* **Does not buy.** A `Secret ℓ A` surface type, declassification, procedures,
  concurrency, I/O, mutable state, termination-sensitivity, timing or any other
  side channel, or any cryptographic property. Termination is the one channel the
  theorem names as open, and N-5 exhibits a well-typed program that spins on one
  secret and stops on another precisely so that the omission cannot be mistaken
  for a result. N-9 formalizes this boundary: when the observer sees
  `nothing` versus `just`, the current typing rules fail termination-sensitive
  noninterference; the spinning run returns `nothing` at every fuel bound.

[[four_distinct_structures]]
== Four distinct structures, and why they stay distinct

Four structures in this family share the shape of an order or a monoid and are
routinely mistaken for one another. They are not instances of one another, no
mapping between them is proved here, and no relabelling is claimed in either
direction.

[cols="2,3,2,3",options="header"]
|===
| Structure | What it indexes | Home | The error it invites

| Confidentiality label `ℓ`
| *Permission to flow*: may data at `ℓ` reach a destination at `ℓ'`?
| here
| Reading the label as "how much this observer knows", i.e. as a standpoint.

| Epistemic standpoint `κ` (modality, warrant)
| *What an agent knows or believes*, and on what evidence.
| `epistemic-types`
| Reading `κ` as a clearance, so a knowledge index silently becomes access
  control.

| Resource grade
| *How much of something a run consumed*: cost, or a high-water mark.
| `tropical-types`, `occupancy-types`, `systemet`
| Reading a bound as a leakage bound. A resource bound measures a run, not what
  an observer learns from comparing two runs.

| Echo residue
| *What distinctions were lost* when an observation collapsed them.
| `echo-types`
| Reading structured loss as a confidentiality property. `EchoSecurity`'s
  no-section result is about a collapsing exit map, not about a low observer.
|===

The reason to hold all four apart is not taxonomy for its own sake; it is that
three of them are accumulations over *one* run and noninterference is a property
of *two*. An accumulation can be perfect and still say nothing about
indistinguishability, and a two-run property can hold while every one-run grade
is unchanged. Where two of the structures genuinely coincide — and today none is
proved to — the coincidence would need its own theorem and its own module name,
not a rename.

== Decision record

* *D153 (2026-09-30, owner).* A secret type = a value whose flow is constrained
  by a confidentiality label with explicit declassification, registered in the
  type-family map on that boundary.
* *D154 (2026-09-30, owner).* Reuse an existing lattice (two-point first, then
  general), prove noninterference, and allow declassification only at explicit
  audited points.
* *Owner confirmation (2026-10-04).* The standalone repository is the chosen
  home. This supersedes the alternative recorded in valence-shell's direction
  doc of folding the work into `epistemic-types`#32, and it resolves the "no new
  repository yet" gate in the origin note (link:https://github.com/hyperpolymath/epistemic-types/blob/main/docs/secret-types.adoc[`epistemic-types`
  `docs/secret-types.adoc`]).

The alternatives considered and *not* selected:

* *Fold into `epistemic-types`* — rejected by the 2026-10-04 confirmation.
  `epistemic-types` remains the correct home of the decision record that started
  this question; it is not the home of a `Secret` API.
* *A grade instance inside SystemET / Anytype* — a candidate for a grade-only
  realisation, still open as a neighbour comparison (SystemET's L2 grade
  algebra, Anytype#15). Not selected here: it would conflate resource-use
  grades with confidentiality propagation unless a mapping is proved, and no
  such mapping exists. See <<neighbours>>.

This section records decisions; it does not claim that any implementation work
has started.

== First model

The material in this section is adopted from the origin note
(`epistemic-types` `docs/secret-types.adoc`, blob `583017cfd5fa`, 2026-09-27) so
that the standalone repository owns its specification. It was written as a
proposal at the boundary set by D154; the calculus it describes is now the one
implemented in `src/SecretTypes/`, with the differences the implementation forced
recorded where they occur (labels are unchanged; variables and lattices became
parameters; termination is named as the open channel). The review checklist at
the end of this document records which items the implementation now evidences —
evidencing an item is not the same as an owner's acceptance of it, and this
document does not claim that acceptance.

=== Use case and trust boundary

The first example domain is a pure, total policy/configuration function that
receives a public request and a trusted private setting and returns an
explicitly classified result. A public observer may choose and know the
request, but must not learn anything about the private setting from public
outputs. This is a small, concrete information-flow problem; it does not claim
to model a deployed service.

Source labels are trusted inputs to the model. The checker cannot infer from an
arbitrary value whether it is genuinely public or private. Any real application
must justify the initial classification at its input boundary; a type
annotation alone cannot authenticate that boundary.

=== Labels, order, flows and clearances

For the first model, exactly two labels:

[source,text]
----
Label = { Public, Secret }
Public ⊑ Public   Public ⊑ Secret   Secret ⊑ Secret
                  (no proof of Secret ⊑ Public)
⊥ = Public        ⊤ = Secret
----

Read `ℓ ⊑ ℓ'` as: data classified at source label `ℓ` may flow to a destination
classified at `ℓ'` without becoming less protected. `Public` is the bottom, an
ordinary flow may raise sensitivity but may not lower it, and combining
dependencies uses the least upper bound (`Public ⊔ Secret = Secret`, etc.).

A clearance is also a label: a value at `ℓ` is within clearance `c` exactly
when there is a witness of `ℓ ⊑ c`. A `Secret` clearance is permitted to
observe either label *inside the model*. A witness states a policy relation; it
does not prove a person's identity, authenticate a credential, or enforce
access control at runtime.

The two-point lattice was the baseline, and D154 made the general case
conditional on the typing rules needing it. What the implementation found, and
what `src/SecretTypes/Lattice/Record.agda` records, is narrower than a
`SecurityLattice` API: generic TINI consumes exactly transitivity of `⊑` (for
principal observers), the two upper-bound laws of `⊔`, and the observer's
down-closure — no decidability, no reflexivity, no antisymmetry, no leastness of
`⊔`, no top. That census is certified by `scripts/minimal-laws.sh` (the theorem
typechecks against a record holding only those laws) and each law is shown
necessary by a countermodel. A general interface is therefore justified only to
the extent of those five fields, and nothing more is claimed.

=== Attacker and observations

The baseline attacker is a low-clearance observer who:

* may choose and know all public inputs;
* may observe the explicitly public projection of a program's result; and
* may compare results from executions with the same public inputs and different
  secret inputs.

The model *assumes* that the attacker cannot inspect secret values directly,
forge trusted source classifications, or obtain a privileged clearance
witness. Those are assumptions, not properties established by any proof.
The language is pure, deterministic and free of I/O, mutable state and
concurrency, so no storage or network channel exists to model. It is *not*
total as implemented: the calculus has `while` with fuel-indexed big-step
semantics, so a run may fail to finish, and termination is the one channel the
theorem names as open (PROOF-STATUS N-5 exhibits a well-typed program that spins
on one secret and stops on another). Timing, space, cache, storage, network,
speculative-execution and other side channels are outside the observation model;
adding any of them later requires a new semantics and threat analysis.

=== Permitted and forbidden flows

Permitted: explicitly trusted public inputs may remain public or be raised to
`Secret`; secret inputs remain secret; values with multiple dependencies take
their join label.

Forbidden: an ordinary `Secret`-to-`Public` flow, including implicit flow. If a
secret condition selects between two different public results, that result must
not be accepted as public merely because neither branch directly returns a
secret value; the condition is a dependency. If commands or effects are added
later, the program-counter (or equivalent control-dependence) discipline must
be specified as well.

There is *no declassification in this baseline*, and as of 2026-11-01 there is
none in the implementation either: no downgrade operation, no release budget, no
trusted declassifier, no authorization policy. D154 admits declassification only
at explicit audited points and none has been specified, so a deliberate release
remains a forbidden flow until a separate policy states who may release which
information, under what evidence or capability, and which security theorem is
preserved.

=== Target semantic property

Let a machine state be a pair of public and secret inputs; call two states
low-equivalent when their public components are equal, with no constraint on
their secret components. Let `run c s` evaluate program `c` in state `s` and
`observePublic` select exactly the output visible to a `Public` observer.
What the implementation proves is the relational form over a store and an
observer, in which a run that does not finish is simply not a case:

[source,text]
----
for every c well-typed under pc, every observer V and stores s ≈[V] s',
  if exec n c s ≡ just t and exec n' c s' ≡ just t', then t ≈[V] t'
  (n and n' independent — the theorem is insensitive to fuel)
----

Instantiating `V` at the principal public observer and the lattice at
`Public ⊑ Secret` is the `Public`-projection statement in the original prose
form. This is a theorem, and it is proved — not an axiom, a field, or a
consequence of having a `Secret ℓ A` wrapper. It was written here as a target
for future typing rules and became `SecretTypes.Noninterference.Generic.tini` on
2026-10-19. Termination remains outside it by name.

The controls the specification required are now fixtures, and they do not stand
in for the theorem: a well-typed public result whose value does not depend on the
secret is accepted; a direct secret flow and a public result selected by a secret
branch are each *refused at their `⊑` obligation* and each *shown to leak* from
low-equivalent stores when the rule is removed (`tests/reject/{ExplicitFlow,
ImplicitFlow}`, `Witness.explicit-leaks`, `implicit-leaks`). A control that only
failed to compile would prove nothing, which is why the leak witnesses exist.

=== Candidate type shape, and its limit

A future value-level surface could include schematic signatures resembling:

[source,text]
----
Secret   : Label -> Set -> Set
raise    : ℓ ⊑ ℓ' -> Secret ℓ A -> Secret ℓ' A
combine  : Secret ℓ A -> Secret m B -> Secret (ℓ ⊔ m) (A × B)
----

These express classification, safe upward propagation and joining
dependencies. They do not define the expression language, its control-flow
rules, or the public observation function. An unrestricted
`Secret ℓ A -> A` — whether called `reflect`, `reveal`, or `readAt` — is not
part of the program interface. A future observer API would need a precise
clearance semantics and a trusted boundary; it still would not authenticate
an actual principal or prove noninterference on its own.

== What this repository does *not* provide

This list is the part of the specification that has *not* changed with the
implementation, and it is checked whenever a claim is added. Two items that were
on it in the 2026-10-04 version are now provided and have moved to
<<status_of_the_model>>: an implemented information-flow type system, and the
noninterference theorem. Everything below remains absent and unclaimed:

* a `Secret`, `classify`, `declassify`, clearance or observer API — the fragment
  has a language, a typing judgement and a store, not a value-level `Secret ℓ A`;
* declassification of any kind, and therefore no audited release point (D154
  permits one; none is specified);
* procedures, concurrency, I/O, mutable state, exceptions, or any treatment of
  termination-sensitive noninterference;
* authenticated principals, runtime access control, cryptographic secrecy,
  secure erasure, zeroization, or protection from timing, cache, storage,
  network or other side channels;
* linear or single-use handling of secret values;
* key provisioning, key rotation or key revocation semantics, and therefore no
  RMO (GDPR/obliteration) key-lifecycle or disclosure guarantee;
* any transfer of proof or code from another repository's algebra, type
  checker or runtime into this project.

The origin note's statements about `epistemic-types` modules
(`Access.Preorder`, `BeliefModality`, `Warrant`, `EchoBridge.Grade` and the
rest) remain statements about *that* repository's narrower interfaces. They are
not re-homed here, and none of them is a confidentiality guarantee.
